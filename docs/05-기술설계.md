# 줍줍! — 기술설계 문서

> GitHub 이슈 [#5](https://github.com/space-joops/joop-joop/issues/5)의 산출물.

## 1. 기술 선택: 프레임워크 없는 정적 웹

| 선택 | 이유 |
|---|---|
| 바닐라 JS (ES 모듈) | 빌드 도구·의존성 0개. 파이썬 개발자도 파일을 위에서 아래로 읽으면 이해되는 구조 |
| Canvas 2D | 원작(joop-03)과 동일한 렌더링 선택. 2D 아케이드에 충분하고 API가 단순 |
| WebAudio 합성 사운드 | 오디오 에셋 파일 없이 코드로 효과음 생성. 저장소가 가볍고 로딩 즉시 완료 |
| localStorage | 서버·계정 없이 최고기록/스킨/설정 저장 |
| Vercel 정적 배포 | `index.html` 그대로 배포. 빌드 단계 없음 |

## 2. 디렉터리 구조

```
index.html          # 단일 페이지. 캔버스 + UI 오버레이
css/style.css       # 카세트퓨처리즘 UI 스타일 (스캔라인, 네온)
js/
  main.js           # 진입점. 게임 루프와 상태 전환만 담당 (파이썬의 __main__ 역할)
  config.js         # 모든 밸런스 수치 상수 (docs/03-게임디자인.md 와 1:1)
  state.js          # 게임 상태 (점수·콤보·생명 등) 생성과 초기화
  joop.js           # 줍 캐릭터: 그리기 + 표정 상태기계 + 애니메이션
  world.js          # 배경: 지구, 별, 궤도 링
  debris.js         # 쓰레기/위험 파편/별조각: 스폰, 이동, 충돌 판정
  effects.js        # 파티클, 점수 팝업, 화면 흔들림
  sound.js          # WebAudio 칩튠 효과음/BGM
  skins.js          # 줍 친구들(스킨) 정의와 해금 로직
  storage.js        # localStorage 읽기/쓰기 (파이썬의 shelve 처럼 단순하게)
  ui.js             # DOM 오버레이: 타이틀/HUD/결과 화면 갱신
docs/               # 한국어 기획·분석·디자인 문서
```

## 3. 코드 컨벤션 — "파이썬 개발자가 읽기 쉬운 JS"

1. **모듈 = 파이썬의 모듈처럼**: 한 파일이 한 가지 책임. 순환 의존 금지.
   의존 방향은 `main → (ui, joop, world, debris, effects) → (state, config, sound, storage)`.
2. **docstring 스타일 주석**: 모든 공개 함수 위에 JSDoc(`/** ... */`)으로
   "무엇을, 왜"를 한국어로 적는다. 자명한 코드에 중복 주석은 달지 않되,
   수식·마법수·게임 감(感) 튜닝값에는 반드시 근거를 남긴다.
3. **클래스는 최소한으로**: 데이터는 일반 객체, 동작은 함수 위주.
   `joop.js`처럼 상태+행동이 강하게 묶인 곳만 클래스 사용.
4. **이름은 풀어서**: `dt`, `ctx` 같은 관용어 외에는 축약하지 않는다.
   (`angularVelocity`, `feverGauge`, `nearMissRadius`)
5. **한 함수 = 한 화면 분량 이내**: 길어지면 쪼갠다.

## 4. 게임 루프 설계

```
requestAnimationFrame 마다:
  dt = 이번 프레임 경과 시간 (초, 최대 0.05로 클램프 — 탭 전환 복귀 시 폭주 방지)
  update(dt):  입력 → 줍 이동 → 스폰 → 오브젝트 이동 → 충돌 → 점수/콤보/피버 → 파티클
  draw():      배경 → 궤도 → 오브젝트 → 줍 → 파티클 → (HUD는 DOM이 담당)
```

- **상태 기계**: `title | playing | gameover` 3상태. 전환은 `main.js`에서만 일어난다.
- **시간 기반 이동**: 모든 움직임은 `dt` 곱으로 계산 → 프레임레이트와 무관하게 동일한 플레이.
- **좌표계**: 지구 중심 극좌표(각도, 반지름). 그릴 때만 직교좌표로 변환.
  파이썬의 `cmath`처럼 `(angle, radius) → (x, y)` 헬퍼 하나로 통일.

## 5. 렌더링 전략

- 캔버스는 CSS 픽셀 × `devicePixelRatio`로 백킹 스토어를 잡아 레티나에서도 선명하게.
- 세로 화면 기준 설계(원작 원칙). 데스크톱에서는 가운데 세로 프레임으로 표시.
- 별 배경은 매 프레임 다시 그리지 않고 오프스크린 캔버스에 1회 생성 후 복사.

## 6. 저장 스키마 (localStorage)

```json
{
  "joopjoop.best": 1234,            // 최고 점수
  "joopjoop.shards": 250,           // 보유 조각
  "joopjoop.unlockedSkins": ["joobi", "amber"],
  "joopjoop.selectedSkin": "amber",
  "joopjoop.muted": false
}
```

- 키에 `joopjoop.` 접두사 — 원작의 `joop_03_` 접두사 규칙을 따른 네임스페이스 습관.

## 7. 배포

- Vercel 정적 사이트. 프레임워크 프리셋 없음(Other), 빌드 커맨드 없음.
- `vercel --prod` 수동 배포 (원작도 수동 배포 원칙).

## 8. PWA (이슈 #14)

원작의 원칙(모바일 세로 PWA)을 계승한다.

| 구성 | 내용 |
|---|---|
| `manifest.json` | standalone, 세로 고정(orientation: portrait), 테마/배경 `#030a05` |
| 아이콘 | `assets/icons/` — 게임의 `drawJoopPortrait()` 코드로 직접 렌더해 생성. 인게임 줍과 100% 동일한 브랜드 |
| `sw.js` | 서비스 워커. **네트워크 우선 + 캐시 폴백** |

서비스 워커 전략을 캐시 우선이 아니라 **네트워크 우선**으로 정한 이유:
- 배포가 수동(`vercel --prod`)이라 캐시 우선이면 옛 버전이 계속 살아남는 사고가 나기 쉽다.
- 네트워크 우선이면 온라인 사용자는 항상 최신, 오프라인 사용자는 캐시로 플레이.
- 파일이 총 20개 미만의 소형 게임이라 매 요청 네트워크 확인 비용이 무시할 수준.

아이콘 재생성 방법: 로컬 서버를 띄우고 브라우저 콘솔에서 `drawJoopPortrait` 를
불러 캔버스에 그린 뒤 PNG로 저장한다 (마스커블은 콘텐츠를 중앙 66%로 축소).
